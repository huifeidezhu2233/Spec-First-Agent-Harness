# 总览与阅读指南

## 这套笔记是什么

这是从一个**已被放弃的项目**里提炼出来的设计思想。项目本身不再维护,但它在"如何把一句模糊诉求,可靠地变成一个真正做对了的成果"这件事上,踩过的坑和想清楚的道理,值得被下一个项目直接吸收。

所以这里**只留思想,不留实现**。你不会在任何一篇里看到代码、技术栈、框架、工具、命令或数据格式——这是刻意的。具体技术会把读者带回"那一个项目当时怎么做的",而那恰恰是最容易误导后来者的东西:换个项目、换个时代,做法早就变了,但底下的判断和取舍不变。每一条原则都被抽象到"换一套技术栈依然成立"的程度,并尽量按 **是什么 → 为什么有价值 → 怎么应用到新项目 → 常见坑** 来写。

一句话:**把它当"设计判断力"来读,而不是"操作手册"来抄。**

## 如果你只带走一条

> **一条把"意图"变成"交付"的管线,真正的价值不在阶段多完整、产物多漂亮,而在于它有没有一个能"判对错"的东西——一个通过真实运行、真实检验来客观裁定"做对了没有"的权威依据(下称"客观验证判据")。没有它,无论叫什么名字,本质上都只是一台永远亮绿灯的文档生成器。**

这条贯穿全篇。它还有一个反直觉的推论:**生成的随机性本身不可怕,昂贵的验证才可怕。** 当验证便宜又客观时,错了就重来、几轮自然收敛;当验证昂贵或主观时,每个错误都在放血。所以工程的杠杆常常不在"把生成变确定",而在"把验证变便宜"。

| [04 执行编排:依赖、批次与并行](04-执行编排-依赖批次与并行.md) | 按依赖组织推进 | 依赖是一等输入,独立的并行、相关的串行;执行若不产出可验证的真实结果,就是走过场 |

**建议路径:**

- **只想抓核心** → 先读本页 + [05](05-验证闭环-可验证性是灵魂.md) + [07](07-经验教训与反模式.md)。这三份能让你在下一个项目里躲开最贵的那几个坑。
- **要落地一套流程** → 顺序读 01 → 02 → 03 → 04,把"收敛—编排—建模—执行"的骨架搭起来,再用 05 给它装上灵魂。
- **系统要活得久** → 读 06 + 08,它们讲的是"第一版之后"的事:健壮、可演进、可协作、不被自己的表象骗过。

## 怎么用这些笔记

- **当检查清单,不当模板。** 每一篇结尾都有"如何应用到你的下一个项目"的要点,拿它去对照你正在做的东西,而不是照抄结构。
- **优先自检那个终极问题:** 假如这一步其实什么都没做对,我的流程会不会照样亮绿灯?只要答案是"会",先别信任何进度。
- **各篇各司其职,交叉处只指路。** 同一个主题只在它的主场篇被详写,其它篇用"参见《…》"引到那里;顺着链接走,不必担心重复。
- **凡"定义了却从不使用"皆为红灯。** 状态、属性、门、控件、指标——建模不等于使用,没有消费端的能力等于不存在。这是从头到尾反复出现的元原则。

---

*这些笔记有意剥离了全部具体技术,只保留可迁移的设计思想与取舍。若你在某处感到"缺了怎么做的细节"——那通常是对的:该由你的项目、你的技术栈、你当下的约束来填,而不是照搬一个已经放弃的项目当年的答案。*
