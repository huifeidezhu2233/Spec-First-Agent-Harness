# 健壮性与可演进设计

一个系统要能被长期依赖，靠的不是"每一步都成功"，而是三件事同时成立：关键能力失败时它优雅退化、让流程继续推进而不是硬崩；"用哪个实现来完成某项能力"没有被写死，可以随项目与环境整体切换；以及每一个产物都自带"我是怎么来的、有多可信"这条信息，便于信任与排错。这三件事分别对应本篇的三个支柱——**降级优先、能力抽象、来源标记**。它们互相咬合：降级让系统始终有东西可产出，抽象让系统能换掉失败或过时的实现，而来源标记是把前两者的代价"诚实地"暴露出来的唯一手段——否则一个降级凑出来的产物会悄悄冒充一等公民。

本篇只谈这三件事的**思想与取舍**。不谈"什么算验证通过、如何逐条核对验收标准"（属于《验证闭环》一篇），也不谈"阶段之间如何门控、按什么顺序推进"（属于《流程编排》一篇）。凡涉及那两类内容，本篇只在必要处一笔带过并指向它们。

## 一、降级优先：把"失败"转化为"降级"

### 1. 为不稳定的关键能力预备一条"必定可用"的兜底路径
- **是什么**：凡是依赖不可靠来源（远端服务、需要凭据的能力、易抖动的外部接入）的关键步骤，都为它配一条本地、确定性、不依赖任何外部条件的替身路径。真实路径与替身路径**共享同一份契约**，产出**结构等价**的产物；真实路径不可用或失败时，流程切到替身，而不是中断。
- **为什么有价值**：外部能力天然易失败。把"能力失败"就地转化为"能力降级"，端到端流程在离线、无凭据、演示、试跑等场景下仍能走通并产出可被下游继续消费的产物。健壮性来自"总有一条能走通的兜底"，而不是"祈祷首选路径不出错"。
- **怎么应用**：先把能力抽象成与实现无关的契约（见第二节）；为该契约提供一个纯本地、确定性的兜底实现，放进默认集合，甚至可作为默认激活项；在编排层用"先试首选、失败即切兜底"的明确顺序把它接起来，并要求兜底产物在结构上合法、可继续消费。
- **常见坑**：
  - **"自动回退"名不副实**。最危险的反模式：文档承诺"失败后自动回退"，但实现里能力层只是抛出一个错误，兜底只是一个需要**手动**切换的独立实现，没有任何一处逻辑真正负责"捕获失败并切换"。落地铁律——自动回退必须**真有一处逻辑负责、且被测试覆盖**，否则它只是文档里的愿望。
  - **兜底靠猜测输入措辞**。如果兜底实现靠关键词/模式去猜输入该产出什么，它会与调用方的措辞强耦合，措辞一改就悄悄失灵；而且这类静态启发式会随领域演进过时，降级质量随之腐化。兜底要么真正确定性、领域无关，要么把领域知识做成可替换的输入而非写死的常量。

### 2. 兜底路径要定期单独演练
- **是什么**：兜底路径平时不走，只在故障时才被触发——这正是它腐化的温床。要把它当成一条**独立的、需定期跑通的路径**来对待。
- **为什么有价值**：一条从没被走过的后备路径，等于没有后备。等真出事时才发现它早已坏掉，是最糟的时机。
- **怎么应用**：为兜底路径准备独立的走查/试跑；把"零依赖、可离线跑通全流程"作为它的常态验收之一；让它成为演示与测试的默认路径，自然获得持续的运行覆盖。
- **常见坑**：只在真实路径挂掉时才第一次运行兜底——那一刻你既在处理故障，又在调试一条从没验证过的路径。

### 3. 每次降级都要"响亮且持久"地被记录
- **是什么**：只要发生了降级，就必须把"发生过降级"这一事实连同**失败原因**记录下来，而不是让降级悄无声息。
- **为什么有价值**：无声降级比直接失败更糟——直接失败至少会引起注意，无声降级会把质量下滑藏起来，让下游误以为拿到了高质量结果。
- **怎么应用**：把"本次结果的来源 + 降级原因"作为产物的元信息一并持久化（详见第五节），并在每个消费界面显式呈现。
- **常见坑**：把降级记录只留在运行期内存里，进程一退就蒸发——这等于没记录。

## 二、在信任边界处防腐：把外部的不确定性挡在门外

### 1. 绝不让自由格式的外部输出直接流入内部状态
- **是什么**：来自不可靠生成器（或用户手填）的输出，一律先经过一层规整，再当作可信数据使用：严格定义内部数据形态，逐属性做类型强转、区间夹逼、去重、丢弃违反结构不变量的条目、属性缺失时回填可计算的确定性默认。
- **为什么有价值**：概率式生成会返回缺属性、越界、重复、指向不存在项等脏数据。在边界处一次性净化，内部逻辑就能始终依赖干净的不变量，"外部的不确定"被隔离在边界之外，内部得以简单可靠。
- **怎么应用**：在外部来源与内部模型之间设一层防腐层；为每个属性定义合法域与缺失时的默认来源；非法即修复而非报错中止。对结构化输入采用两级容错解析——先按理想形态严格解析，失败再退化为"从噪声里抽取最外层有效片段"，并剥除常见包裹前后缀；对数值配置用"解析失败回默认并夹取到安全下限"的统一模式。
- **常见坑**：**什么都默默修好的规整层会默默掩盖一个严重跑偏的生成器**。宽容解析一旦悄悄"救回"了本应报错的坏输入，上游缺陷就被藏起来。必须在修补/退化路径上留下**可观测痕迹**（例如修补计数、降级记录），让"这次修补量很大"这件事可见，从而区分"偶发容错"与"上游一直在发坏数据"。这一点与第五节的来源/质量标记强相关：净化层要与质量信号配对，而不是无声吸收。

### 2. 让不变量"由构造天然成立"，而不是事后补检
- **是什么**：把关键结构保证编码进生成规则本身，使违规在构造上就不可能发生（模式级例子：只允许引用比自己更早的条目，于是引用关系天然无环、无前向悬空）。
- **为什么有价值**：一次性消灭一整类下游错误，且省去运行期检测的复杂度。
- **取舍要正视**：这类单向/线性依赖约束不是无代价的纯收益——它以牺牲表达力换取干净。它天生无法表达某些合理的反向或交叉依赖，硬套会逼你把本该相互引用的关系拆歪。是否采用，取决于"消灭一类下游错误"与"损失一部分表达力"孰轻孰重，别用"结构看起来干净"去换"结构其实不对"（此取舍的完整讨论归《需求与任务建模》，本篇口径与其保持一致）。
- **怎么应用**：在"给生成器的指令"和"边界校验"两处**同时**施加同一约束。
- **常见坑**：只写在给生成器的指令里是不够的——生成器随时会违反；不在边界兜底强制的不变量，永远只是愿望。（"什么才算合规"的判定标准归《验证闭环》一篇，本篇只强调"两处同时施加"这条健壮性原则。）

## 三、能力抽象：把"用哪个实现"藏到统一契约背后

### 1. 用与实现无关的契约约束所有实现，由集中构造点做选择
- **是什么**：定义一份最小的能力契约——若干动词化的能力方法、一个"是否就绪"的自检、一个"自我描述"；所有实现都只满足这份契约。调用方只依赖契约，由一个集中的构造点按配置把"标识"映射成具体实现，未知标识回落到最通用、最安全的默认。
- **为什么有价值**：让"换能力提供方/换实现"从"改调用方"退化成"改配置"；新增实现只需满足契约并在构造点登记；调用方与实现解耦，也便于注入测试替身。
- **怎么应用**：把各实现的共性逻辑抽到一个共同基座；构造点做成无副作用的映射，给未知标识一个安全默认；调用方从头到尾只见契约、不见实现。
- **常见坑**：**两类抽象渗漏都要防**。其一，通用契约里混进只对某类实现才有意义的专有属性，让"通用配置"承载了非通用语义；其二，反过来，公共契约里的某个通用旋钮只被部分实现真正兑现（例如一个"输出上限"参数只对一类实现生效、另一类完全忽略），使用者以为调了通用旋钮，对部分实现却无效。原则：**公共属性要么被所有实现兑现，要么明确标注适用范围；专有参数塞进一个通用扩展位，而不污染公共契约。**

### 2. 用命名"配置档案"承载分环境/分能力提供方接入，可整体切换
- **是什么**：把一组接入参数打包成一个具名档案；系统保存多个档案并记录"当前激活的是哪个"；切换环境或能力提供方，只是切换激活档案的名字，而非改实现。
- **为什么有价值**：同一套实现在开发/演示/生产、在不同能力提供方之间切换无需动源码；新增一个自定义接入点就等于"加一个档案"；配置意图集中、可版本化。
- **怎么应用**：把"档案集合 + 激活档案名"存进项目内的配置产物；提供增删改查、设为激活、连通性自检等操作；删除时维护不变量——至少保留一个，删掉当前激活档案时自动改指到其它档案，保证系统永不进入不可用状态。
- **常见坑**：通用解析逻辑里出现"按某个特定档案名做特判"的分支（写死的常量），让只有那个名字的档案享受某些兼容回退，自定义档案却拿不到——这直接违背"档案对等、能力提供方无关"的初衷。**特判应改为按能力类别或显式开关驱动，而不是按名字。**

### 3. 允许按流程阶段分别绑定能力
- **是什么**：除了全局激活档案，还允许为流程中每个具体步骤单独指定用哪个档案；未指定的步骤自动继承全局激活。
- **为什么有价值**：不同阶段对能力的诉求不同（有的要强、有的要快/省、有的可用兜底）；按步骤绑定能同时兼顾成本、质量与稳定，也便于灰度（只让某一步切到新实现试跑）。
- **怎么应用**：维护一张"步骤→档案"的覆盖表，解析时"步骤覆盖优先、否则回落全局激活"；提供设置/清除某步骤覆盖的操作。
- **常见坑**：**步骤名是散落在编排各处的隐式契约**。若无集中登记，拼错一个步骤名会"静默回落"到全局档案而不报错。应把步骤名做成受控的显式取值集合或集中常量，并对未登记的步骤名给出告警。另一条相关反模式——**配置剧场**：只应暴露真正会改变行为的控件。给一个根本不调用该能力的纯规则阶段、或一个只用于渲染状态角标的伪阶段也提供"选哪个实现"的旋钮，会让人以为设置生效、实则空转，侵蚀信任并浪费排障时间。逐一审查每个暴露的旋钮是否真的抵达一条真实执行路径。

### 4. 能力要能自省：就绪自检 + 自我描述
- **是什么**：每个实现都能回答两件事——"我是否已就绪"和"我是谁"（用什么外部接口、外部能力等摘要），并能吐出一份规范化的结构化状态供诊断。
- **为什么有价值**：在真正发起昂贵且易失败的调用**之前**先做就绪判断，是优雅降级的前提（第一节的"先试首选、失败即切兜底"里，"先试"能被"先判断就绪"进一步前移）；自我描述让运维和用户一眼看清当前接入，大幅降低排障成本。
- **怎么应用**：在契约里内建"是否就绪""人类可读描述""结构化状态"三类自省能力；把它接到面向用户的状态查询入口；对无需凭据的本地兜底实现，就绪自检可直接判定为"已就绪"。
- **常见坑**：**能力应以"行为可验证"来确认，而不是以命名或配置取值来宣称**。一个被命名为"并行"的执行单元内部却是逐个串行，一个被判为"多路"的分支实际仍逐个串行执行——占位式命名会误导调用方以为已拿到某种能力收益，还掩盖了真实问题。就绪自检要检验真实行为，不要只回一个恒真的标志位。

## 四、分层配置与安全默认：让接入可演进

### 1. 配置来源分层，优先级明确，取首个非空
- **是什么**：运行时配置由多个来源叠加，优先级清晰（进程级注入 > 项目本地覆盖 > 档案默认 > 内置默认），后者只在前者缺失时生效，取第一个非空值。
- **为什么有价值**：既能把稳定默认写进可提交的共享配置，又能让每个环境/每个人做本地或临时覆盖而不动共享配置；可预测的优先级消除"到底哪个值生效"的困惑。
- **怎么应用**：写一个按固定顺序尝试各来源、取首个非空的解析器；为每个可覆盖项设计命名规范（如按档案名派生作用域前缀）避免不同档案互相串扰；在文档里明确列出优先级与命名规则。
- **常见坑**：同一项存在多套并行作用域前缀（长前缀、短前缀、遗留名），实现全兼容但文档只展示其中一种，长期必然与实现漂移，使用者不知道到底该设哪个。**应收敛命名，或至少在文档里穷举所有被接受的别名及其优先级。**

### 2. 区分"持久化的定义"与"解析后的运行时值"
- **是什么**：把可提交、稳定的档案定义，与合并了覆盖、经过校验规整后的运行时配置，分成两种不同的东西：定义参与持久化，运行时值参与调用。
- **为什么有价值**：定义保持干净可版本化，运行时值承载易变与敏感信息；边界清晰后，既不会把临时或敏感值意外写回共享配置，也让"存储"与"消费"各取所需。
- **怎么应用**：定义只存"稳定意图"（含"敏感凭据来自哪个引用"这类指针）；解析步骤产出运行时结构（含真正取到的值、规整后的数值、就绪自检结果）；只允许定义结构参与持久化。

### 3. 敏感凭据按引用存储，展示时脱敏
- **是什么**：配置里不存凭据本身，只存"它来自哪个外部引用的名字"；任何对外展示都对敏感值脱敏（只露头尾，或标注为"未配置"）。
- **为什么有价值**：让配置产物可安全提交与分享；避免凭据进入日志或诊断输出；把"凭据值"与"凭据位置"解耦，轮换时无需改配置。
- **怎么应用**：档案里放"凭据来源名"属性，运行时才去实际读取；提供一个统一的脱敏展示逻辑供所有状态/诊断输出复用。

### 4. 开箱即用的内置默认 + 向上探测项目边界
- **是什么**：配置产物缺失时用一套内置默认让系统立即可跑；项目根与本地覆盖通过"从当前位置逐级向上寻找标志物"来定位，而非要求用户显式给路径。默认集合里就含一个可离线的兜底实现，保证"零配置也能走通流程"。
- **为什么有价值**：降低首次使用门槛，无论从项目内哪个子目录调用都能正确锚定范围与本地覆盖；这也是降级优先的自然延伸——默认状态就是"可离线走通"。
- **怎么应用**：提供一个幂等的"生成默认配置"操作（仅在缺失时写）；用"逐级向上找标志物"确定项目根；把安全、可离线的兜底实现放进默认集合。
- **常见坑**：向上探测若找不到标志物而**静默**回落到"当前目录"，在深层或非常规目录下可能锚错项目根却不报错。宜在探测失败时给出可见提示，而非无声地用兜底路径。

## 五、来源标记与可追溯：让每个产物自带"出身"

### 1. 给每个产物打上"来源 + 可信度"标记
- **是什么**：为每个产出的工件标注它是怎么来的——主生成路径 / 降级后备路径 / 确定性默认——以及为什么（降级时附上失败原因），让下游据此判断该产物的可信程度。
- **为什么有价值**：一个高投入生成的结果和一个"降级后套模板"的通用结果，**外观可能一模一样**。来源标记是区分二者的唯一线索，是"从意图到结果可追溯"的关键一环，也是诚实交接的基础——接手者只有知道产物出自"高能力生成"还是"降级回退"，才能校准对它的信任、决定是否需要人工复核。
- **怎么应用**：为每个工件记录"生成来源"与一条说明；在生成时刻和总体状态里都展示；对经过大量净化修补的产物，把"这次修补量很大"也作为一种质量信号一并记录（呼应第二节）。

### 2. 来源信息必须与工件一起持久化——这是最容易名不副实的地方
- **是什么**：来源标记的价值，全部取决于它是否与工件一起持久化。只活在单次运行内存里、每次运行都被清空的来源标记，**等于没有提供可追溯性**。
- **为什么有价值**：这是"从意图到实现全程可追踪"的物理基础。若持久化的工件登记只记了路径与生成时间，唯独没记来源，那么最有价值的那条信息——"这份产物到底是主路径产出的，还是失败后降级凑出来的？"——会在进程退出后蒸发，一个降级产物之后完全可以冒充一等公民。
- **怎么应用**：把"来源 + 说明"当作工件元信息的一等属性，和工件本体一起持久化；工件登记里必须有这一项。把产物本身当作下一级读取的"事实来源"时，来源信息要随之可读。
- **常见坑**：**"建模了却不持久化"是本类设计最典型的失败**。抽象教训——凡是声称提供可追溯性的属性，都要问一句："进程退出后它还在吗？"不在，就是空头承诺。

### 3. 来源标记要在每一个消费界面都呈现
- **是什么**：来源信息只有在"工件被消费的每个界面"都展示才真正有用。
- **为什么有价值**：只在某一个入口显示、另一个入口不显示，会让一部分角色"盲用"降级产物，可追溯性对他们形同不存在。
- **怎么应用**：把来源展示接到所有面向用户/接手者的状态查询与产物浏览入口；不要让某个界面私自省略它。
- **常见坑**：多界面各自实现展示逻辑，久而久之部分界面漏掉来源项；共享逻辑应留在内核，由各界面统一派生，而非各写一份。

### 4. 用只增不改的动作痕迹支撑"随时间发生了什么"
- **是什么**：把"当前产物是什么"（来源标记回答的）与"随时间发生过哪些动作"分开：后者是一条按时间排列、只追加的动作痕迹——每次改变状态的关键动作（生成、降级、编辑、覆盖、回滚、配置变更）都留下一条带时间戳、且尽量带"谁发起"的记录。
- **为什么有价值**：来源标记回答"这一份产物出身如何"，动作痕迹回答"这一路是怎么走过来的"，二者合起来才是完整的可追溯性，也是"接手别人半成品"的支柱。
- **怎么应用**：抽一个集中的动作记录器；确保它在存储层真正做到只增不改（而不是"每次把整份历史读出、追加、再整体写回"这种既非崩溃安全也不可扩展的伪追加）；记录里包含"动作发起者"，而不仅是动作本身，否则跨角色的问责无从谈起。
- **常见坑**：把"结构化进度状态""可审阅产物""只增审计痕迹"这三种职责混在一份存储里、又缺唯一属主，是潜伏的数据腐坏源——本篇不展开状态与门控（见《流程编排》），但"来源/审计这一路的持久化要有单一属主、且真正只增不改"属于本篇的可追溯性底线。

## 如何应用到你的下一个项目

- **先抽象，再降级**：把每项不稳定的关键能力先收敛到一份与实现无关的契约，再给它配一条确定性、必定可用、结构等价的本地兜底。没有契约，降级就无处安放。
- **让"自动回退"真有逻辑负责**：不要在文档里承诺回退却在实现里只抛错。指定一处逻辑负责"捕获失败→切换兜底"，并用测试覆盖它。定期单独演练兜底路径，别等出事才第一次运行它。
- **每次降级都留痕**：记录"发生过降级 + 原因"，并让它响亮、持久、随工件一起持久化。无声降级比失败更危险。
- **在信任边界处防腐**：外部输出一律先规整（强转、夹逼、去重、回填默认）再进内部；但要让"修补量"可见，别让防腐层默默掩盖跑偏的上游。
- **能力选择靠配置，不靠改实现**：用命名档案承载分环境/分能力提供方接入，可整体切换；允许按阶段单独绑定；删除时维护"永不进入不可用状态"的不变量。
- **警惕两种抽象渗漏**：专有属性别污染公共契约；公共旋钮要么被所有实现兑现、要么标注适用范围。
- **配置分层、优先级明确、安全默认**：来源优先级写清楚、取首个非空；定义与运行时值分离；凭据只存引用、展示脱敏；零配置也要能离线跑通。
- **来源标记必须持久化、且处处可见**：只在内存里的来源标记等于零可追溯。工件登记要有"来源"这一项，所有消费界面都要展示它。
- **由构造保证不变量时，正视表达力代价**：单向/线性依赖约束能一次性消灭一类下游错误，但会损失表达力，权衡口径见《需求与任务建模》。
- **用一句话自检每个"名"**：这个被叫做"并行/自动/门/校验"的东西，是否有可验证的行为兑现它的名字？能力以行为确认，不以命名宣称——这是贯穿健壮性设计的元原则。
- **划清边界**：本篇管"失败怎么退化、实现怎么切换、产物怎么留痕"；"什么算验证通过"交给《验证闭环》、"阶段之间怎么门控推进"交给《流程编排》，不要在这里重复。
